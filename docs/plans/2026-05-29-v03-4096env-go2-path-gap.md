# v0.3 Blocker — the "4096-env Go2" GPU step path does not exist yet

> **Status:** OWNER DECISION REQUIRED — blocks p01 Waves 2–3 (Go2 baseline + optimization) and, downstream, p04.
> **Raised:** 2026-05-29, during p01 entry (perf baseline). **Does NOT block:** p01 Wave 1 (timing infra + tooling — already landed).
> **Why this is an owner call:** resolving it picks the S1 hot-loop architecture, which master-plan §5.2 forbids an agent
> from choosing speculatively. The four v0.3 phase specs assumed this path already existed; it does not.

## 1. The finding

v0.3's flagship (S1) is **4096-env Unitree Go2 articulated locomotion with contacts, on GPU, < 1 ms/env-step**. A read-only
audit of the engine shows **no code path can step an articulated Go2 with ground contact at any env count today.** The two
GPU step paths are disjoint and neither does it:

| | Single-env Featherstone path | Batched path |
|---|---|---|
| Entry | `nuka::c_abi::StepWorldGpu` (`src/c_abi/world.cpp:151`) | `runtime::gpu::StepBatchedCudaWorld` (`src/runtime/gpu/batched_device_world.cu:3035`) |
| Dynamics | **true reduced-coordinate Featherstone ABA** (`FeatherstoneAba::ApplyPositionDrives/ComputeAccelerations/Integrate`, `world.cpp:169,176,180`) | free rigid-body integration + **maximal-coordinate** contacts/joints/drives as constraint rows (`batched_device_world.cu:3064,3088-3123`) |
| Articulation? | yes (ABA) | **none** — grep for `featherstone`/`articulation`/`aba` in `batched_device_world.cu` returns nothing |
| Contacts? | **disabled** (`record->step_options.enable_contacts = false;`, `world.cpp:255`) | yes (broadphase + narrow-phase + contact rows) |
| Env count | **C ABI hard-caps `env_count != 1` → `NOT_SUPPORTED`** (`world.cpp:235`) | N instances, but only ever fed trivial fixtures |

Supporting facts:
- **The C++ `World::CreateFromScene(device, scene, env_count, dt)` (`src/include/nuka/nuka.hpp:86`) is not an independent
  multi-env surface** — it forwards to `nuka_world_create_from_scene` (`nuka.hpp:101,106`), which enforces the `env_count==1`
  cap. The v0.3 gate-test spec assumes this builds a 4096-env world; today any `env_count!=1` returns `NOT_SUPPORTED`.
- **The batched joint/drive solver has only ever been fed toy topology** — a single static-parent + 1-child revolute hinge
  (`tests/perf/test_cuda_batch_joint_drive_timing.cpp:26-58`). It has never seen Go2's 12-DOF tree.
- **The only "4096" perf test steps 4096 *free rigid boxes*** (no joints, no Go2) via `StepCudaWorld`
  (`tests/perf/test_cuda_step_timing.cpp:18`). Go2 is exercised **single-env only** (demo + `test_go2_stand_5s`).
- **Partial good news:** the articulation cooker emits one `ArticulationCookedTopology` per disconnected root body with **no
  cap** (`src/runtime/articulation/articulation_cooker.cpp:95,126-132`), and the Featherstone kernels already grid
  per-articulation (`featherstone_aba.cu:580` `dim3 grid(state.articulation_count)`). So N Go2 skeletons in one cooked scene
  *would* produce N articulations the ABA kernels parallelize over — but nothing builds such a scene, the C ABI caps env at
  1, and contacts are off on that path.

## 2. What is and isn't blocked

- ✅ **p01 Wave 1 (done):** in-engine CUDA perf timing infra (`src/core/perf/*`) + sweep/compare tooling + perf-budget doc.
  These are path-independent and already committed.
- 🔴 **p01 Wave 2–3 (blocked):** "instrument the 4096-env Go2 step loop" and "capture the 4096-env Go2 baseline" presuppose a
  step path that doesn't exist. Optimizing kernels (`row_solver.cu`, `featherstone_aba.cu`, `contact_generation.cu`) toward a
  Go2 budget is premature until we know *which* path runs the workload.
- 🔴 **p04 (downstream):** 4096-env Go2 PPO needs the same path.

## 3. Options (owner picks; I do not choose the architecture)

### (a) Build batched warp-per-articulation Featherstone + contact rows — "the plan as written"
Implement the S1 hot loop the master plan and `docs/architecture/perf-budget.md` actually describe (Featherstone ABA
80 µs + PGS row solver 500 µs line items). **Pro:** matches the stated architecture and the §7 budget; reduced-coordinate is
the right long-term path for diff-sim (v0.5). **Con:** this is essentially *building S1's core engine path* — large, and the
four phase specs never scoped it as its own phase. Effectively a missing foundational phase before p01 optimization is meaningful.

### (b) Drive 4096-env Go2 through the existing batched maximal-coordinate joint/drive + contact solver
Feed real Go2 joint topology into `StepBatchedCudaWorld`'s constraint solver; keep the single-env Featherstone path for the
§7 exit-criterion #5 oracle (no regression). **Pro:** likely "wire up + validate," not "new solver"; fastest route to a real
4096-env Go2-with-contacts baseline; this is how Isaac Gym/Lab (our p03 compat target) does large-scale locomotion. **Con:**
reinterprets the S1 architecture (maximal- vs reduced-coordinate) → **needs owner sign-off**; the perf-budget's Featherstone
line no longer maps; reduced-coordinate diff-sim (v0.5) would still need building later.

### (c) Scope p01 to what runs today + insert an explicit foundational phase
Land p01 against existing paths only: keep the timing infra, capture **labeled relative baselines** for the batched-rigid
4096-env path and the single-env Featherstone Go2 path, and land the parameterized gate-test scaffolding (records-and-skips).
Then add a named foundational phase (**p01.5 / p0**) to build the chosen 4096-env Go2 path before p03/p04. **Pro:** honest,
unblocks measurable progress now, defers the architecture call without faking a Go2 baseline. **Con:** the headline "4096-env
Go2 < 1 ms" baseline slips to the new phase.

## 4. Open scoping unknown (matters mainly if owner leans (b))

Does the batched joint-block solver handle **Go2's 12-DOF branching tree** (4 legs × 3 joints + floating base), or only the
simple hinges it has been tested on? If only simple hinges, (b) becomes a solver extension, not cheap wiring. A short scoping
spike can answer this — **but only after the owner chooses a direction.**

## 5. Recommendation

No agent-chosen architecture. If forced to rank for *time-to-a-real-baseline*: **(b)** (pending the §4 spike) reaches a true
4096-env Go2-with-contacts number fastest and aligns with the p03 Isaac-Lab compat story; **(a)** is the most faithful to the
master plan but is a foundational build; **(c)** is the safe honest fallback that keeps p01 moving without faking the headline.
The master plan (§7, perf-budget) currently encodes the **(a)** architecture, so **(b)** specifically requires an owner
amendment. Recorded here for the owner; await decision before any path-building work.

## 6. Owner decision (2026-05-29): option (a) — build batched Featherstone + contact rows

The owner chose **(a)**: implement the master-plan S1 hot loop — **batched warp-per-articulation Featherstone ABA +
contacts solved as constraint rows** (via the existing PGS row solver, coupled through articulation Jacobians), D1-preserving.
Faithful to master-plan §7 / `docs/architecture/perf-budget.md` (the 80 µs ABA + 500 µs row-solver line items) and keeps the
reduced-coordinate path needed for v0.5 diff-sim.

Consequence: a **foundational sub-phase `p01-F`** is inserted ahead of the original p01 Wave 2–3 (instrument + baseline +
optimize), since those presuppose a runnable 4096-env Go2 path. p01-F builds that path:
1. Batched N-articulation device state + env replication (cook/replicate Go2 into 4096 articulations in one device world).
2. Batched ABA stepping over 4096 articulations (the `featherstone_aba.cu` kernels already grid per-articulation).
3. **Contacts for articulated bodies** — broadphase + narrow-phase against Go2 shapes, contact Jacobians, contact
   (+joint-limit) rows solved by the existing row solver and coupled back into ABA (the genuinely new coupling work).
4. C ABI / C++ `World` surface to create + step a 4096-env Go2 world (lift the `env_count==1` cap, or a batched-articulation builder).
5. Integrated validation: 4096-env Go2 steps stably on GPU; single-env Featherstone oracle (§7#5) unchanged; D1 preserved.

Detailed file-level plan: `docs/plans/2026-05-29-v03-p01F-batched-featherstone-contacts.md`. Only after p01-F lands do Wave 2
(instrument the real Go2 step loop) and Wave 3 (optimize toward the budget) become meaningful.
