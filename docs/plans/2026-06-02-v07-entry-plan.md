## 2. Interface reality — what v0.5 left for v0.7 (start mid-stream)

v0.5 closed the open-source + diff-sim phase. The pieces v0.7 builds ON (do not rebuild):

- **Self-written sparse solver + seam (the big one).** `class SparseLinearSolver`
  (`src/diffsim/sparse_solver_backend.hpp:115`, factory `MakeSparseSolverBackend` `:133`,
  header comment `:112` "the seam v0.7+ extends") + `SelfWrittenCgBackend`
  (`sparse_solver_cg.hpp:51`): CG + Jacobi / Block-Jacobi, deterministic fixed-order dot/SpMV,
  fp64-accumulate/fp32-store, D1 bit-exact. **p01 hardens this; p02/p03 add MINRES/ILU,
  GMRES/AMG on the same seam** (those four were explicitly deferred v0.5→v0.7, master plan
  `:238,:920,:961`). So p01 is "continue mid-stream," not a from-scratch solver.
- **Diff-sim spine.** Tape + gradient checkpointing + `RecomputeOrchestrator` + `backward_runner`
  (`src/diffsim/`), C-ABI `nuka_diffsim.h` (`nuka_tape_*`, `grad_parameters_out`), PyTorch
  `nuka.autograd` + JAX `nuka.jax_frontend` (bit-identical D1; ~1e-6 cross-framework), link-mass
  parameter gradient (`backward_runner` `grad_mass`, direct-dynamics, FD-validated).
- **Codegen adjoint path.** 4 base row classes (ids 0–3: contact/joint/drive/featherstone_contact),
  schema `adjoint_evaluator`, `adjoint_emitter`/templates, the V3 FD harness
  (`src/codegen/v3_validation/`). **v0.7's 7 new row classes (ids 4+) reuse this path** —
  author IR YAML + adjoint rules, FD-validate, no new codegen machinery.
- **IFT contact gradient (partial).** `ift_runner.cu` ships `grad_qdot_free` + `grad_b_c` for
  the PGS Delassus path — but fixed-base, sticking-equality only, and **d/dM,d/dJ deferred**
  (`ift_runner.cu:28-36`). See §4.B — p08 supersedes this with the SDF-contact path.
- **OSC forward + adjoint** (gains Kp/Kd + task target differentiable; `dL/dq` deferred,
  `osc_adjoint.hpp:36-42`). **Workstream-C control modes** (PD/Torque/Velocity/ComputedTorque/
  OSC/Actuator) all forward + per-mode adjoint.
- **Sim2real N1+N2** (Philox counter-based sensor noise + domain randomization, D1, oracle-safe
  off-by-default) — `src/sensor/noise/`, `python/nuka/noise.py`. **N3 (p-level in v1.0) extends this.**
- **Engine substrate.** GPU-resident 12-phase step, `phi::Buffer`/`DeviceContext`, SAP broadphase
  (p04 replaces), hand-rolled `.usda`/MJCF/URDF import (tinyxml2 for XML; NO OpenUSD), Vulkan
  offscreen renderer (p12/p13 add the self-written CUDA RT, a distinct pipeline), the V1 oracle +
  physics-smell lint + D1 determinism gates.

## 3. Cross-cutting risks (carry-forward + new) — read before dispatch

- **R-A — Featherstone↔XPBD coupling instability (master plan §8 `:960`, "S2-blocking, Medium).**
  Mitigated by p11's tuning (sub-stepping, λ warm-start, correction clamp via `SolveConfig`) and
  fully addressed in **v1.0 p01** (sub-step orchestrator). v0.7 needs it *functional* for the rigid
  grasp; production stability is v1.0.
- **R-B — D1 determinism is a NET-NEW burden on every new primitive.** Each new kernel must hold
  byte-exact two-run: `stable_sort` for Morton/LBVH (`p04:69`), **integer-only** atomics in LBVH
  bottom-up / RT persistent-thread (allowed; `p04:105`, `p12:142`), and ALL grid/query/contact/
  particle outputs **sorted** before consumption. Extend the physics-smell lint scope to
  `src/collision/**`, `src/runtime/{soft,fluid,sdf}/**`, `src/rt/**`, `src/import/cooker/**` as each
  lands (mirrors the v0.5 `src/diffsim`/`src/sensor` scope extensions).
- **R-C — memory envelope.** p05 cross-system candidates capped at 16/particle; p07 naïve
  50K×800KB = 40 GB → **SDFs MUST be shared per-mesh across instances** (dedup to ~80 MB); p10
  ~180 MB/1M particles. Bake the caps into the specs' acceptance, and `log()` any silent truncation.
- **R-D — solver schedule risk (carry-forward, master plan §8 `:961`, High).** De-risked for the
  GATE because p01–p03 are OFF the demo critical path (the rigid-cup demo needs no MINRES/GMRES).
- **R-E — Newton-through-thin-shell** (`p08:172`): clamp the Newton step to `voxel_size` so a
  particle can't punch through a 0.5 mm panel.
- **R-F — external/CI deps:** p06 vendors V-HACD (MIT/BSD); p15 needs Houdini Vellum / Flex /
  MuJoCo-3.0-SDF oracles + Git-LFS goldens (<1 GB). Cook-time host-CPU work (p06/p07) is the only
  sanctioned exception to the GPU-only rule (`p06:7`, master plan §5.6).
- **R-G — the three deferred diff-sim channels (§4).** Two are latent/unowned in the specs as
  written; this plan assigns them.

## 4. Diff-sim gaps + contact-force readout — INSERTION DECISIONS (the new scope)

v0.5 closed with three diff-sim channels deferred (§4.A–C); §4.D is an owner-requested scope
addition (2026-06-02). The 16 v0.7 specs, as written, do not all pick these up. Below: what each
is (source-verified), and where it lands.

### 4.A — Floating-base ORIENTATION-channel gradients → **NEW v0.7 phase, off critical path**

- **What (verified `step_backward.hpp:52-56`):** the velocity channel of the floating-base adjoint
  is EXACT in v0.5; the **orientation** channel is deferred — `a_grav = R(base_rot)ᵀ·g`'s
  dependence on base rotation + the quaternion POSE integrator are not differentiated (base
  orientation held fixed; supported seeds are `q'/qdot'/v_root'`, NOT `base_pose'`).
- **Owner in the specs: NONE.** A re-grep of all 16 v0.7 specs for base_pose/a_grav/quaternion/
  articulation-adjoint finds no pickup. p16 only *exercises* diff-sim with a rigid cup + scripted
  trajectory (`p16:124`), which never seeds `base_pose'` — so the gate doesn't force it, but it
  stays a hole in the articulation adjoint.
- **INSERTION — add a new v0.7 phase `p08b — Floating-base orientation adjoint completion`**
  (numbered to sit beside the contact-adjoint work without renumbering the spec'd phases). Scope:
  extend `step_backward`/`aba_reverse` with (i) the `R(base_rot)ᵀg` derivative w.r.t. base
  rotation and (ii) the quaternion pose-integrator reverse; seed `base_pose'`. This is the
  "bounded contact-free completion of the p02-A spine" the v0.5 notes anticipated — pure
  articulation diff-sim, NO contact/solver dependency.
  - **Schedule:** in the **p01–p03 solver slack, OFF the demo critical path**, but BEFORE v1.0.
    Rationale: v0.7 is where the diff-sim spine lives; closing it here means v0.7 ships a *complete*
    articulation adjoint, so v1.0's dynamic whole-body demos (pour/wring, where the base reorients)
    and any diff-sim/RL-through-base-motion build on a finished foundation rather than re-opening
    core math mid-stage.
  - **Validation (reuse the v0.5 floating recipe):** FD gate `<1e-3` on a `g≠0` scene with a
    deliberately reorienting free base + a `base_pose'` loss seed (the `MultiStepGradVsFD_Floating`
    pattern), plus D1 two-run byte-exact backward. Extend `tests/diffsim/test_aba_reverse_fd.cpp`.
  - **Decision (§6-1, RATIFIED 2026-06-02):** inserted in v0.7, in the p01–p03 solver slack, off
    the critical path. The v0.5 "deferred to v0.7" note is now an owned v0.7 phase (`p08b`).

### 4.B — d/dM, d/dJ contact-derivative channels → **scope clarification in p08 (not a new phase)**

- **What (verified `ift_runner.cu:28-36`):** the v0.5 PGS/IFT contact path ships `grad_qdot_free` +
  `grad_b_c` but defers `d/dM` and `d/dJ` (the `d(A⁻¹) = −A⁻¹ dA A⁻¹` + `M⁻¹Jᵀ` product-rule
  channels). That path is also already fixed-base + sticking-equality only.
- **Owner in the specs: p08**, but indirectly. p08 (Newton-on-summed-SDF contact) delivers the
  **full analytical adjoint of the new SDF-contact rows** via IFT-at-convergence — exactly the
  `d(A⁻¹)` machinery (`p08:101`, master plan §3 Round 5 path-3 `:222`, Round 7 `:352`). But it
  closes the derivatives for the **new `RigidSDFContactRow` / `FeatherstoneSDFContactRow`**, it does
  NOT retro-fill the v0.5 PGS `ift_runner.cu`.
- **INSERTION — make the supersession explicit in p08's scope; no new phase.** Decision to record:
  **the SDF-contact rows are the differentiable contact path from v0.7 forward; the v0.5 PGS
  `ift_runner.cu` d/dM,d/dJ channels are NOT retrofitted (superseded, not retro-filled).** The
  PGS path remains a forward/V3 reference. p08's acceptance must include `d/dM` and `d/dJ` FD
  validation for the SDF rows (so the channel is genuinely closed where it now lives).
  - **Decision (§6-2, RATIFIED 2026-06-02):** (a) SDF-only differentiable contact; the PGS-path
    d/dM,d/dJ retrofit is NOT commissioned. p08 documents the supersession and FD-validates
    d/dM,d/dJ for the SDF rows. (If a future workload revives the PGS contact path needing its
    contact gradient, re-open as a bounded task then.)

### 4.C — semantic + normal/uv sensor modalities → **split: normal/uv into v0.7 p14, semantic a small v1.0 task**

- **What (verified):** master plan promises "+ semantic + normal/uv" sensors at v1.0 (`:81`,
  `:535`; §10 maps Semantic="RT + instance ID buffer", Normal/UV="RT byproduct" `:501-502`). But
  **no v1.0 phase implements them**, and p14 explicitly defers semantic ("No semantic segmentation
  (v1.0)", `p14:233`). Meanwhile the v0.7 RT framebuffer ALREADY produces them: `framebuffer.hpp`
  has `normal`, `albedo`, `primitive_id` (`p13:179-181`, the prim_id comment literally says "for
  semantic / instance segmentation"), and the triangle intersect already returns barycentric
  `{u,v}` (`p13:65`). So the *data* exists at the RT layer in v0.7; only the *sensor surfacing* and
  the *semantic class map* are missing.
- **INSERTION — split by cost:**
  - **normal / uv → fold into v0.7 p14** (the sensor phase). They are pure RT byproducts already in
    the framebuffer; exposing them as DLPack-able sensor channels is near-free buffer plumbing on
    top of p14's `sensor_buffer_layout.hpp`. Doing it in p14 avoids re-touching the sensor buffer
    layout again in v1.0. (Small scope add to p14; flag in §6-3.)
  - **semantic → a small dedicated v1.0 task** (genuine new work: the cooker must assign semantic
    class ids to meshes/instances, then map `primitive_id → class` at sample time). Slot it into the
    v1.0 N3-sensor group (e.g., a `v10-p04b — semantic segmentation sensor`), since it pairs with the
    sensor-realism work and needs cooker support, not just an RT byproduct.
  - **Decision (§6-3, RATIFIED 2026-06-02):** normal/uv pulled into v0.7 p14; semantic → a small
    v1.0 task (`v10-p04b`). The previously-unscoped table promise is now scoped to concrete phases.

### 4.D — General per-link contact-force readout (MuJoCo-parity) → **broaden v0.7 p14; decouple from RT**

- **What the owner asked (2026-06-02):** beyond the SDF differentiable-contact path, the contact
  force on a given robot limb must be obtainable on the *normal* forward path — like MuJoCo's
  `mj_contactForce` / per-body contact force, queryable for any link at any step, not only as a
  byproduct of the SDF/diff path.
- **Reality (verified):** the engine ALREADY computes per-contact λ (normal + friction impulse) in
  the PGS solve (`constraint::RowBuffers` `row.lambda`, `TotalNormalLambda`; `articulation_contacts`).
  But the ONLY contact field exposed to the C-ABI / Python today is `NUKA_FIELD_CONTACT_POINTS`
  (`src/include/nuka/nuka.h:130`) — there is **no contact-force / λ field**. p14's tactile + F/T
  design (Tasks 7.14.4 / 7.14.5) already reads λ but only for a **pre-declared "sensorized link" /
  "wrist sensor frame"** (`p14:92,109`), and is "essentially zero-cost: Phase 5 already computes the
  lambdas; the sensor just collects + reshapes" (`p14:105`).
- **INSERTION — broaden p14's force/torque scope to a first-class, ANY-link, contact-model-agnostic
  readout:**
  - **New field `NUKA_FIELD_LINK_CONTACT_WRENCH`** — per link, the net contact force + torque
    (world frame, about the link origin/COM), aggregated from ALL contact rows incident to that
    link: plain rigid PGS contact, SDF contact (p08), and coupling contacts (p11) alike → **NOT
    SDF-specific.** Impulse→force conversion: PGS λ is an impulse (N·s), so the readout reports
    **force = λ / dt** (MuJoCo reports forces, not impulses).
  - **Plus MuJoCo-`mj_contactForce` parity:** a per-contact enumeration per link (contact point,
    normal, normal force, friction force) in a CSR layout — p14's tactile layout already does this
    for sensorized links; generalize to all links and expose through the C-ABI.
  - **Available on the PLAIN forward path** — reads the existing λ, requires no SDF, no diff-sim, no
    RT. This is the "平常也要能获取到" requirement: a normal observable in any `step()`.
  - **C-ABI + nanobind + DLPack, SoA over envs** → usable as a 4096-env RL observation / sim2real
    signal, zero-copy like the other state fields.
  - **Decoupled from p13:** unlike RGB/depth, this needs only the contact solve (present since v0.5),
    so it can land EARLY in v0.7 and does not wait on the RT pipeline. Recommend **splitting p14 into
    p14a (contact-force / tactile / F-T — early, no RT dep) + p14b (RGB / depth — needs p13)**.
  - **Differentiability note:** the *readout* is a plain observable. If a loss is seeded on contact
    force, the gradient rides the SDF-contact adjoint (p08) where it exists; the v0.5 PGS contact
    path stays forward-only per §4.B.
- **Decision (§6-6, RATIFIED 2026-06-02):** broaden p14 to the any-link contact-wrench + per-contact
  readout, contact-model-agnostic, on the plain forward path, DLPack-exported; split p14a (contact
  force, early, no RT) from p14b (RGB/depth). New field `NUKA_FIELD_LINK_CONTACT_WRENCH` + a
  per-contact C-ABI query.
- **Implementation notes (verified 2026-06-02 — the data already exists; this is a readback, no new
  physics):**
  - All per-slot contact data is ALREADY in the batched world
    (`src/runtime/gpu/batched_articulated_world.hpp`), fixed stride `kMaxFootContactsPerEnv = 4`,
    `SlotCount() = env_count × 4`: `ContactPointBuffer()` (Vec3 world point per slot),
    `ContactLinkBuffer()` (uint32 **GLOBAL link index** per slot), `ContactDepthBuffer()`, and the
    SOLVED impulse via `DownloadLambda()` (device buffer `env×slots×3` = `{λn, λt1, λt2}` per slot,
    `:290-291`). `dt` is in the step params (default `1/240`, `:103`).
  - The ONE missing accessor: per-slot contact **normal + tangent basis (t1,t2)** (computed
    internally by `ComputeContactTangentBasis` / carried in `ArticulatedContactRow` — expose a
    `ContactNormalBuffer()` + tangent accessor, or read from `DownloadRows()` /the row Jacobians).
  - **Wrench kernel** (per env, per link): `F_world = Σ_slots[link] (n·λn + t1·λt1 + t2·λt2) / dt`;
    `τ = (contact_point − link_origin) × F`; output `[env, link, 6]` device buffer served as
    `NUKA_FIELD_LINK_CONTACT_WRENCH` (stride 6 floats), aliasing pattern per `buffer.cpp` batched
    arm (mirror the `CONTACT_POINTS` branch, `buffer.cpp:200`). **D1:** fixed-order sum over the ≤4
    slots (atomic-free). Sum ALL contact models incident to the link (rigid PGS now; SDF p08 +
    coupling p11 later) so it stays contact-model-agnostic.
  - **Per-contact query (mj_contactForce parity):** expose the existing per-slot
    `{point, normal, link, λn/λt1/λt2}` as a CSR-by-link C-ABI enumeration — most buffers already
    exist; only the normal accessor is new.
  - **Surface:** new `NUKA_FIELD_LINK_CONTACT_WRENCH` enum (`nuka.h`) + `buffer.cpp` batched arm +
    nanobind `.value(...)` + DLPack; a `test_link_contact_wrench.cpp` (foot-stance net force ≈
    `body_mass·g`, D1 two-run byte-exact) + a python DLPack smoke; lint scope += the new kernel dir.
  - **State-sensor surface for context (verified 2026-06-02):** `qpos`/`qvel` ALREADY exist as
    `NUKA_FIELD_JOINT_POSITION`(2)/`JOINT_VELOCITY`(3); 16 fields total are exposed + DLPack-able
    (link poses/spatial-vel, base pose, drive targets/gains, torque/velocity/actuator inputs, task
    target, contact points). **Contact force is the only materially-missing state sensor** — §4.D
    closes it. (If MuJoCo-style `qacc`/`cacc` are later wanted, those are a separate small add.)
