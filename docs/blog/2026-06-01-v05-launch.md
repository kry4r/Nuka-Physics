# Nuka Physics v0.5: a deterministic, differentiable GPU physics engine goes open source

*2026-06-01*

Today we are open-sourcing **Nuka Physics** — a GPU-resident, strongly
deterministic, differentiable CUDA physics engine for robotics and reinforcement
learning — under the Apache License 2.0. v0.5 is the first public release.

This post covers what Nuka is, what shipped in v0.5, the demo that proves the
differentiable pipeline works end to end, how Nuka differs from Isaac Lab / Brax /
MJX, and where it is going.

## What is Nuka Physics?

Nuka is a physics engine built for embodied robotics and large-scale RL training,
with three commitments baked in from the architecture up:

1. **It runs on the GPU and stays on the GPU.** Thousands of articulated
   environments simulate in parallel on a single card from one cooked world
   template — 4096 Unitree Go2 quadrupeds is the v0.3 anchor demo.
2. **It is strongly deterministic.** No floating-point atomics, fixed reduction
   order in every physics path — so a run reproduces *byte-for-byte* across two
   executions. We call this the **D1** contract, and a lint enforces it on every
   pull request.
3. **It is differentiable.** Nuka exposes a *full analytical reverse-mode adjoint*
   through its rigid and articulated dynamics. You can backpropagate a scalar loss
   through a simulation rollout and get exact, engine-consistent gradients.

Nuka is a C++ engine with a stable C ABI and thin nanobind Python bindings, so it
embeds directly in a C++ host as well as driving from Python.

## What shipped in v0.5

v0.5 turns the v0.3 forward-sim foundation into a **differentiable** engine and
opens the source. Concretely:

- **Full analytical reverse-mode adjoint** through rigid + articulated dynamics.
  Featherstone Articulated Body Algorithm (ABA) is differentiated in reverse mode
  (a 3-pass reverse over the articulation tree). This is a real analytical
  adjoint, not a stop-gradient approximation.
- **A recorded tape with gradient checkpointing.** The backward replays the
  forward from periodic checkpoints to regenerate intermediates on demand, so
  memory stays bounded rather than growing with every step.
- **An implicit-function-theorem (IFT) contact gradient at convergence**, solved
  with a **self-written deterministic sparse solver** (CG + Jacobi / Block-Jacobi,
  fixed-order reductions, D1 bit-exact). No closed-source SDK is used anywhere.
- **Parameter and control-mode gradients** — including the link-mass channel the
  demo below exercises.
- **Zero-copy PyTorch + JAX interop** via DLPack. Engine buffers alias torch / jax
  tensors with no copy, and both frontends drive the *same* deterministic engine
  adjoint.
- **Sim-to-real noise**: N1 per-field sensor noise (Gaussian / Poisson) and N2
  per-episode domain randomization, both built on a counter-based Philox4x32-10
  RNG so they are deterministic, replayable, and oracle-safe.

We are equally clear about what v0.5 does **not** yet do. The differentiable
rollout path is single-env and contact-free; the floating-base **orientation**
channel and the d/dM, d/dJ contact-derivative channels are **deferred to v0.7**.
Soft body, fluid, and rigid↔soft↔fluid coupling are also v0.7. We would rather
ship an honest scope than over-claim.

## The demo: gradient-based system identification on Go2

The v0.5 headline demo recovers an **unknown link mass** by gradient descent
through a differentiable rollout — the end-to-end proof that the diff-sim
infrastructure works.

**What it is, precisely:** a contact-free, fixed-base, direct-dynamics mass
recovery. The Go2's base is rigidly fixed and there is no ground contact. A
constant rest-pose PD target is held while the robot sags under gravity; the
actuated joint velocities `qdot` after a short transient are a function of the
link masses through `qddot = M⁻¹ · (τ_PD − τ_gravity)`. Minimizing the mean
squared error between the simulated `qdot` and a ground-truth `qdot` (generated
with a known true mass) recovers that mass.

**What it is not:** this is mass *system identification*, not locomotion. The
gradient does not produce a gait — there is no contact here. The fixed-base +
`obs="qdot"` configuration is the engine's clean differentiable mass channel.

The setup: a single thigh link (global index 2), true mass `1.4 kg`, start guess
`0.9 kg`, a `K = 30`-step rollout, Adam at `lr = 0.03` over a fixed 80-iteration
budget. The mass is passed as a **torch tensor** via `params=` (calling `.item()`
would sever the autograd graph), and the gradient comes from the engine's
`grad_parameters` via a single `tape.backward`.

The recovered mass climbs from the 0.9 kg guess, overshoots slightly (Adam's

|----------|-------|
| Recovered mass | **1.400448 kg** (true: 1.4) |
| Relative error | **3.2015e-04** — ~31× under the 1% success bar |
| Loss reduction | 3.376617e-02 → 2.542075e-08 (**~1.33 × 10⁶×**) |
| Mass gradient at start | `-1.389748e-01` (genuinely nonzero — the basin is non-flat) |

The demo writes `run_log.txt` and `convergence.csv` to
`examples/demos/go2_system_id_results/`, plus `loss_curve.png` / `mass_curve.png`
*if matplotlib is installed* (skipped gracefully otherwise). A cheaper, fixed-seed
version runs in CI as `python/tests/test_go2_system_id_convergence.py`.

That last row matters as much as the recovered mass: the **same** optimization,
run twice, produces a **bit-identical** parameter trajectory. Determinism is not a
side feature here — it is a property the gradient pipeline preserves end to end.

## What makes it different from Isaac Lab / Brax / MJX

### Figure 4 — the layered architecture

```
  ┌─────────────────────────────────────────────────────────────┐
  │  Python frontends:  nuka.autograd (PyTorch)   nuka.jax_frontend │
  │                     zero-copy DLPack tensor interop            │
  ├─────────────────────────────────────────────────────────────┤
  │  C ABI  +  nanobind bindings  (libnuka, embeddable in C++)     │
  ├─────────────────────────────────────────────────────────────┤
  │  Diff-sim:  tape · gradient checkpointing · reverse-mode step  │
  │             adjoint (Featherstone ABA) · IFT contact gradient  │
  │             · self-written deterministic CG solver             │
  ├─────────────────────────────────────────────────────────────┤
  │  Runtime:   batched CUDA world · contact/joint/drive solve     │
  │             · Featherstone ABA forward · PD drives             │
  ├─────────────────────────────────────────────────────────────┤
  │  CSR universal constraint rows  ·  class-blind scheduler       │
  ├─────────────────────────────────────────────────────────────┤
  │  Scene:  MJCF / URDF / text-USD import  ·  cooker  ·  template  │
  └─────────────────────────────────────────────────────────────┘
       GPU-resident, CUDA-only production backend  ·  D1 determinism
```

**Full analytical adjoint vs Brax's stop-gradient.** Brax and MJX are
differentiable JAX simulators, but Brax's contact gradient is a stop-gradient
approximation. Nuka's adjoint is the analytical reverse of the same deterministic
Featherstone kernels the forward ran — gradients are exact and engine-consistent.
(In v0.5 the differentiable path is contact-free; the contact-derivative channels
arrive in v0.7.)

**Strong determinism vs non-deterministic PhysX / Isaac Lab.** PhysX-backed runs
are not bit-exact across executions. Nuka's D1 default is byte-for-byte
reproducible, and the *same gradient path* run twice gives a bit-identical
parameter trajectory. A D2 weak-determinism toggle is reserved at the C ABI for
workloads that would trade reproducibility for speed.

**Same engine adjoint across PyTorch and JAX.** Both frontends call the *same*
`tape.backward`. As a result, `jax.grad` and torch's `loss.backward()` produce
gradients that **agree to engine round-off** — a regression gate requires a
relative error below `1e-4`, and in practice we see ~1e-6. (We reserve the phrase
"bit-identical" for the D1 two-run determinism guarantee, not for the
cross-framework comparison, which takes different host arithmetic routes into the
same adjoint.)

**Direct C++ embedding vs Python-only.** Nuka is a C++ engine with a stable C ABI;
the Python package is a thin layer over it. You can embed `libnuka` directly in a
C++ host.

**Honest on performance.** The IFT contact-gradient path is not a speed play.
Measured against the tape on the rigid + Featherstone scope, IFT runs at
**0.65–0.69×** — i.e. slower, because it is launch-bound at small active-row
counts. Its value is **constant memory** (no growing tape), D1 determinism, and
correctness at the fixed point. We frame the broader performance target as a
qualified close, not a speedup.

## Roadmap

v0.5 closes the open-source + diff-sim phase. The
[master plan](../plans/2026-05-28-nuka-physics-master-plan.md) §7 lays out the
phase exit criteria that govern the path forward (no calendar dates — phases
close when all criteria pass):

- **v0.7 (S2 entry):** XPBD soft / cloth rows, PBF fluid, the SDF cooker + Newton
  contact with analytical adjoint, V-HACD convex decomposition, an LBVH broadphase
  upgrade, and RGB / depth / tactile / force-torque sensors. This is also where
  the deferred diff-sim channels (floating-base orientation; d/dM, d/dJ contact
  derivatives) land. Anchor demo: H1 grasp a cup and place it on a table.
- **v1.0 (S2 polish):** K2 + K3 rigid↔soft↔fluid cross-system coupling, a
  self-written CUDA RT pipeline, and Vulkan↔CUDA external-memory interop.
- **v1.5 / v2.0 / v3.0:** warehouse-scale multi-robot scenes, the VLA RGB +
  semantic + depth data factory, and eventually real-hardware sim-to-real.

The self-written sparse solver shipped in v0.5 (CG + Jacobi / Block-Jacobi) is the
core that v0.7+ extends with MINRES / ILU(0) / GMRES / AMG — the caller-facing API
stays stable, so new methods are transparent.

## How to contribute

Nuka is Apache 2.0 with a Contributor License Agreement. To get started:

1. Read [CONTRIBUTING.md](../../CONTRIBUTING.md) for the build flow (Linux, CUDA
   12.8, g++-10, `build-cuda128`), the test gates, and the two documented
   known-fail oracle tests that are expected and are *not* regressions.
2. Sign the **CLA** — the CLA-assistant bot checks every PR; a PR can't merge
   until the check passes.
3. Run the **physics-smell lint** locally (`python tools/lint/physics_smell.py`).
   It must pass: it blocks float atomics in physics paths (the D1 contract),
   hot-path allocation, throwing across the C ABI, and more.
4. For larger changes, propose an amendment to the
   [master plan](../plans/2026-05-28-nuka-physics-master-plan.md) — it is the
   source of truth for the architecture and roadmap.

Try the demo, read the [getting-started guide](../getting-started.md), and tell us
what you build. Nuka is now public — we are excited to see where the community
takes a deterministic, differentiable GPU physics engine.

— The Nuka Physics Authors
